# Marketplace Stripe Connect sandbox payments design

Status: proposed for review; planning only. No product changes, credential validation, database changes, provider setup, or deployment are authorized by this document's creation.

## Purpose and baseline

Add one cohesive guest Marketplace payment flow: prove seller email ownership, complete Stripe-hosted onboarding, buy one explicitly fictional item through hosted Checkout, and confirm its simulated sale from a verified webhook. Preserve Board, People, profiles, custom authentication, listing publication, browsing, photos, and private inquiries on the existing Supabase/Vercel projects.

Inspected on 2026-11-17: this Orca worktree is `Famanias/stripe-connect-payments-plan`, based on `15fbf94690b5d64bab57724f09f4cc0145f4dcd3`; local `main`, `origin/main`, and remote `main` match. PR #1 is merged. No applicable `AGENTS.md` was found in the repo or checkout ancestors. Lockfile versions are Next.js 15.5.29, React 19.3.1, Supabase JS 2.119.0. The nine-file `tsx --test` command passes 37 tests. These are local baseline results, not payment acceptance results.

Actual seams: `features/marketplace/types.ts` and `validation.ts` define explicit public DTOs; `lib/server/marketplace-store.ts` owns Supabase and private writes; `marketplace-handlers.ts` injects stores for tests. Migrations use service-role-only invoker RPCs, explicit grants, RLS, and empty search paths. Browse returns only active listings; `find()` currently rejects sold items. Existing `fb08_session` authenticates Board/People through `auth.ts` and `route-helpers.ts`, not Supabase Auth. People is `/?view=people`, not `/people`. Scripts use Node, `--env-file`, `--import=tsx`, and operator-only dry-run/`--apply` conventions.

Read alongside `docs/MARKETPLACE_IMPLEMENTATION.md`, `docs/MARKETPLACE_DEMO_DATA.md`, and the companion implementation plan. The supplied original Marketplace prompt and HTML establish the compact Tahoma/classic-blue visual direction; their old implementation/deploy directives do not authorize work in this planning handoff.

## Fixed constraints

- Preserve the existing React 19 / Next.js 15 App Router / TypeScript / Supabase / Vercel application and nostalgic Marketplace styling.
- Use only assessor-provided shared Stripe sandbox credentials; never use live keys, real cards, real identity documents, real bank details, or real inventory for payment QA.
- Use direct charges on the seller connected account with a 10% application fee; all money movement and payouts are simulated.
- Enable purchases only for explicitly classified sandbox listings belonging to a verified seller whose Stripe readiness has been confirmed.
- Signature-verified webhook processing, never a redirect or browser parameter, confirms paid status and marks the correct sandbox listing Sold.
- Keep seller contacts, buyer data, connected account IDs, order authorization proofs, and provider secrets out of public listing DTOs, HTML, metadata, logs, and public database reads.
- Keep Board/People custom sessions separate from Marketplace seller and buyer proofs; no ordinary Marketplace login or registration flow.
- Apply only additive Marketplace migrations; never replay or repair unrelated historical migrations or overwrite existing listings.
- No implementation, dependency installation, migration application, Stripe credential use, webhook registration, hosting configuration, deployment, sending, or submission is authorized during planning.

## Decisions proposed by this plan

### Seller authority without account registration

The assessment's literal email-only shortcut lets anyone redirect another seller's payments. Do not implement it, even behind a demo switch. Instead, the seller enters their private listing email and a short-lived email verification code, then clicks **Connect with Stripe**. This creates a private verified-email payment identity, not a Board user or a Supabase Auth user. All eligible sandbox listings whose private contact matches that verified email use that identity, including subsequent listings. Matching uses `lower(trim(email))`; do not collapse plus addressing or provider-specific dots. This case-folding is a deliberate product convention.

Use a six-digit cryptographically random code, a 10-minute challenge, at most five attempts, single-use atomic consumption, and a random 32-byte browser nonce. Store only a domain-separated HMAC of the code bound to challenge ID, email, and browser nonce hash. Issuing a new challenge invalidates earlier challenges for the same email and browser. Challenge creation returns the same generic 202 response and random selector whether a listing exists or not. Never return/log the code or disclose contact matches. Limit sends to three/hour/email and ten/hour/IP; verification attempts also have a 30/hour/IP budget. Reuse persistent rate counters with payment-specific action names. Expired, replayed, wrong-browser, and exhausted challenges fail uniformly.

A successful code exchange creates a revocable, opaque 32-byte seller capability stored hashed in Supabase, with a one-hour expiry. Use an HttpOnly, Secure, SameSite=Lax, Path=/ cookie (`__Host-fb08_mp_seller` in HTTPS; an unprefixed development equivalent). It authorizes only that normalized email and payment tenant. Every payment destination action checks this persisted session. Do not let a posted email or account ID replace a connected destination. Expiry requires email verification again; it does not detach existing accounts or unbind listings.

**External prerequisite:** the repo currently has no email delivery. Proposed provider is Resend's HTTPS send API, behind an injected `SellerMailer` adapter, with server-only `RESEND_API_KEY` and `MARKETPLACE_SELLER_EMAIL_FROM`. A verified sending domain and an operator-controlled recipient inbox must be available before hosted QA. Provider setup/DNS changes require later authorization. This email sends ownership codes only; it does not add inquiry notifications. Fail closed if delivery is unavailable. Never expose an OTP bypass on a public deployment. Local tests inject an in-memory mailer. A controlled inbox is used only for private ownership verification; all Stripe identity/buyer/bank fields remain fictional test data. Do not send the verified private listing email to Stripe automatically.

### Explicit inventory isolation

Add public `inventory_kind` with values `ordinary`, `demo`, `sandbox`, default `ordinary`. Only `sandbox` can be reserved or sold by this flow. The new-listing form has an unchecked **Fictional sandbox item — test payments only** control and explicit notice; existing creation behavior defaults to ordinary. Classification is a seller assertion for newly created fictional inventory, not permission to reclassify existing rows through an arbitrary public update endpoint.

The existing 21 stock-photo fixtures become `demo`, not automatically purchasable. Their `.invalid` email cannot pass verification. Keep their descriptions, photos, contact rows, prices, and status untouched. Identify them by the deterministic SHA-256 fixture IDs from `seed-marketplace-demos.ts` and the checked-in JSON manifest, then verify exact expected title, description/credit, price, category, display name, image path and private contact within an operator transaction before classification. A mismatch aborts the whole apply; a missing fixture is reported, never created implicitly. A `[Demo]` title alone proves nothing. New seeder runs must classify only their exact validated IDs; unchanged reruns are idempotent.

For acceptance, create new clearly fictional sandbox listings with the controlled inbox using the normal form and verification flow. Do not assign the 21 fixtures to that inbox, bypass ownership, or convert ordinary listings. Sandbox orders include `livemode=false` and a deployment-specific tenant. A paid sandbox order changes only its sandbox row to `sold`. Sold listings leave the active feed/count/search but retain a public detail URL with **SOLD · SANDBOX** and no Buy Now or inquiry form. Removed listings remain 404. Ordinary active listings retain their private inquiry flow.

### Stripe integration and compatibility gate

Choose Accounts v1 with controller properties for this narrowly specified assessment's snapshot `account.updated` event contract; Stripe now recommends Accounts v2 for new general-purpose integrations. This compatibility choice is intentional, not a claim that v1 is the newest API. Use full Stripe Dashboard access, Stripe requirement collection, Stripe payment-loss responsibility, and connected-account fee responsibility (`controller.stripe_dashboard.type='full'`, `requirement_collection='stripe'`, `losses.payments='stripe'`, `fees.payer='account'`). Use Stripe-hosted `account_onboarding` Account Links. Never store links or return them to an unverified seller. Refresh/return pages require seller proof; a return alone never means ready.

Before enabling the feature during authorized implementation, privately verify the supplied test key's platform identity, Connect permission, allowed connected-account country, availability of the selected controller configuration and hosted onboarding, card capability, PHP presentment/settlement constraints, application-fee support, and ability to register Connect snapshot webhooks. Configure an operator-selected supported `MARKETPLACE_STRIPE_ACCOUNT_COUNTRY`; do not infer it from the site's PHP prices or assume Philippine connected accounts are available. Check platform/country specifications and complete an owned test account/Checkout in preview. No silent switch to destination charges, live mode, another account model, currency conversion, or a different platform. A missing capability blocks live QA and Buy Now; report the precise blocker while local implementation can still proceed after authorization.

Readiness requires a freshly retrieved known account with matching tenant/seller metadata, the selected fee controller, `details_submitted`, `charges_enabled`, `payouts_enabled`, active `card_payments`, and no disabling requirements. Treat a deleted/inaccessible account or failed refresh as not ready. Recheck immediately before session creation; cache only for display for at most 60 seconds. `account.updated` refreshes from the API rather than trusting stale event ordering. Do not change Stripe platform-wide settings. Onboarding/retry creation uses a durable seller creation key and unique database mapping so two clicks cannot create/reassign two destinations; ambiguous calls remain pending.

### Money and Checkout

Use the official `stripe` Node SDK server-side only, exact installed version in package.json/lockfile and a recorded compatible non-preview API version. Hosted Checkout uses its returned URL; no Elements, Stripe.js, or browser SDK is needed. Preserve the required public environment name even though this redirect-only flow does not consume it client-side.

Only one listing, quantity one, `mode='payment'`, `payment_method_types=['card']`; no delayed methods, taxes, shipping, coupons, currency conversion, adaptive pricing or session recovery links. Create all Checkout/PaymentIntent/Charge/balance retrievals on the locally recorded connected account using SDK `stripeAccount` options. No `transfer_data` or `on_behalf_of` destination-charge variant.

The reserve RPC snapshots `(price * 100)::bigint` directly in SQL. Never recompute payment amounts from the public DTO's floating-point `price` or accept a client price. Currency is `php`. For this test feature the allowed gross is 10,000–99,999,999 centavos (PHP 100.00–999,999.99); smaller/zero or larger ordinary listings remain valid listings but cannot be purchased. This conservative business bound is not Stripe's universal minimum. Compatibility checks and Stripe errors still apply.

Fee rounding is half-up to one centavo: `feeMinor = floor((grossMinor + 5) / 10)`. PHP 1,234.50 → gross 123450, application fee 12345, seller remainder 111105 **before Stripe processing fees**. Put the application fee in `payment_intent_data.application_fee_amount`. Snapshot values are immutable. Metadata on Account, Checkout Session and PaymentIntent uses `fb08_app='marketplace-payments-v1'`, tenant, opaque local seller/order/listing IDs as appropriate; no emails, cookie tokens, or inquiry text. Metadata is an attribution hint, not authorization.

For evidence, retrieve the connected Charge balance transaction and distinguish `stripe_fee` from application-fee components; `balance_transaction.net` already accounts for fees and must not have the application fee subtracted again. Store actual settlement currency/gross/fee components/net separately. If settlement is not PHP, show both currencies with provider-derived values; never invent FX or subtract mixed currencies. Missing balance data means **Fee details pending**, not a claimed 90% net. The platform's application fee is 10% of the customer PHP amount; simulated seller net also includes applicable processor fees. No real payout is asserted.

### Reservation and order state

Persist an order before any Stripe call. Under a listing row lock, validate tenant, sandbox status, seller email mapping, and readiness; snapshot the account, amount, fee, currency and buyer proof hash. Enforce one holding order per listing with a partial unique index covering `preparing`, `open`, and `review`, plus one paid order per listing. An additional unique `(tenant,buyer_access_hash,submission_key)` provides retry identity. Same key/different listing is 409. Concurrent buyers: one wins, others get 409 without creating Checkout.

Order states: `preparing → open → paid`; `preparing/open → expired` only after a definitive unpaid-terminal reconciliation; inconsistencies become `review` and keep the inventory locked. Paid is terminal. Persist the exact Checkout creation parameters and stable idempotency key `tenant:checkout:orderId:v1`. Set a fixed session expiry 31 minutes after initial preparation, with unchanged params on retry. Retry session creation only while that timestamp is still valid and within a 23-hour idempotency safety budget. An ambiguous provider/DB response never frees inventory, never creates a replacement session, and never retries under a new key. If the original request can no longer safely be retried, freeze for operator reconciliation. Stripe's idempotency retention is not an indefinite guarantee.

Do not release a reservation based on a local timer, cancel redirect, server error, unpaid completed event, or expired event payload alone. Retrieve the stored session on its account. Release only if Stripe confirms it expired/unpaid and any associated PaymentIntent cannot still succeed (cancel it if permitted and verify `canceled`; processing/succeeded/unknown keeps the hold or finalizes payment). A `checkout.session.expired` event is the one additional necessary subscription for abandoned holds; an operator reconciler covers missed events. A completed session that is not paid stays held for reconciliation. A card-only configuration does not remove the need for delayed webhook handling.

The webhook may arrive before the create response is attached to the order. It may atomically attach that first canonical session only to the matching preparing order after complete account/metadata/amount/fee validation; a different already-bound session becomes review. Hold/paid uniqueness and listing status changes are in the same RPC transaction. Never hold a database transaction open across Stripe HTTP calls.

### Webhook trust and guest confirmation

`POST /api/marketplace/stripe/webhook` is a public HTTPS Node route, raw bounded bytes (1 MiB), SDK signature verification against `STRIPE_WEBHOOK_SECRET`, standard timestamp tolerance, and no browser-origin requirement. All other state-changing browser routes enforce exact configured app origin plus Fetch Metadata, JSON/multipart limits, persistent rate limits, and appropriate seller/buyer proof. Do not reuse Board's provider-error logger for payments.

Subscribe with `connect:true`, snapshot format, and exactly `checkout.session.completed`, `account.updated`, `checkout.session.expired`. Match the pinned API version. No wildcard subscriptions. Verify the signature first, then return 200 for foreign tenant/account/order IDs and unsupported/live-mode events without persisting their payloads or looking up their Checkout objects. Known local objects require local account mapping, tenant, `livemode=false`, exact order/listing/account/session/PaymentIntent IDs, quantity one, PHP gross and fee, and canonical paid state. A mismatch never sells an item: record a minimal private rejection/review reason and return 200. Infrastructure/API failures on known work return 503 for retry.

Use unique `(tenant,event_id)` receipts and atomic fulfillment: record successful receipt, set order paid, and set its still-held sandbox listing sold in one transaction. A failure rolls back the receipt too. Duplicate semantic events with different IDs still cannot sell twice. Retrieve current account/session state to handle out-of-order delivery; never demote paid or use event timestamps as a total order. Persist only allowlisted event identifiers/outcome codes, no raw webhook body or customer details. Fee enrichment can retry separately without blocking an already-verified sale.

Before Checkout, a same-origin buyer-session POST issues an opaque 32-byte browser capability (`__Host-fb08_mp_buyer`, HttpOnly/Secure/Lax/Path=/, seven days). Orders bind its domain-separated hash and a seven-day read expiry. Checkout requires that cookie; the browser retains a UUID submission key for retries. `/marketplace/orders/[orderId]` and its status API require both the valid UUID and matching buyer capability, return uniform 404 otherwise, are dynamic/no-store/noindex, and expose only item summary, status and allowed amount fields. No token in query strings, Stripe metadata, localStorage or logs. An order ID or Checkout session ID alone grants no access. Losing the cookie requires starting a new browsing session; do not promise email recovery in this scope. A denied read never reserves another item or changes order state.

Success URL is the order page on a fixed configured app origin, without authorization parameters; it polls persisted status every two seconds for up to 60 seconds, then offers a manual refresh and accurate **Payment confirmation pending** copy. Only `paid` shows **Sandbox payment confirmed**. Cancel returns to the listing without releasing its reservation. Failed/declined card attempts can retry the same open hosted Checkout while held.

## Deployment, evidence, and limits

Environment names: required assessment names `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`; existing Supabase/service/session names; new server-only `MARKETPLACE_PAYMENTS_ENABLED` (default false), `MARKETPLACE_PAYMENT_TENANT`, `MARKETPLACE_APP_ORIGIN`, `MARKETPLACE_STRIPE_ACCOUNT_COUNTRY`, `RESEND_API_KEY`, `MARKETPLACE_SELLER_EMAIL_FROM`. Validate test key prefixes without logging values, but only authorized provider calls can establish validity/capability. A missing configuration disables purchases. Use separate tenants/accounts/orders for local, stable preview, and production even if Supabase is shared; do not allow a preview webhook to fulfill production orders. Bind each new sandbox listing privately to its server-configured payment tenant atomically at publication, before ownership verification or Checkout, so previews cannot consume unclaimed production sandbox inventory. Ordinary/demo inventory is never bound. The purchase kill switch stops new Checkout creation while existing webhooks, order reads and reconciliation keep working.

During later authorized implementation, prepare a stable public HTTPS preview webhook URL before testing. If Vercel preview protection blocks Stripe, use an authorized route-level public exception or a stable unprotected QA alias; do not disable project-wide protection silently. Register only this application's exact endpoint, securely enter its signing secret in the appropriate Vercel environment, then redeploy that target. Production uses `https://fb08.vercel.app/api/marketplace/stripe/webhook` with its own endpoint secret/tenant. A CLI listener has a different signing secret. Never log registration responses containing the secret, delete other candidates' endpoints, or turn off another endpoint. Provider endpoint limits are a blocker to resolve with the assessor, not permission to remove someone else's configuration.

Verify preview before production. Live acceptance requires fictional seller hosted onboarding, Buy Now → hosted Checkout, 4242 test card success, webhook-confirmed private Supabase order and correct Sold row, accurate application fee and fee-aware simulated seller result, and continued Board/People/listing/inquiry flows. Capture screenshots of onboarding, Checkout, success and a redacted private DB row with status, amount, tenant and test-mode proof. Redact contacts, cookies, keys, IDs that grant access and personal data. Deliver live Marketplace URL, public repository URL, reviewer notes; optionally a ≤3-minute video. Prepare submission notes for `apply.capm.us`, choice **4) Stripe Connect**; never send/submit automatically.

Rollback disables new checkouts and restores the prior app deployment only after preserving a working webhook/reconciliation path for outstanding sessions. Keep new additive tables/order audit records. Do not drop payment data or reset ordinary inventory. Operators may reset only exact sandbox fixture IDs after all related Stripe sessions are terminal; retain previous orders and their uniqueness semantics by using new fixture IDs for repeated sales.

**Residual shared-key risk:** signature validation authenticates delivery from Stripe, not this candidate. Other key holders may inspect or mutate our sandbox Accounts/Sessions/metadata, generate events, and affect simulated balances; the sandbox owner can see data sent there. Local mapping, tenant metadata and exact monetary binding reduce accidental crossover but cannot provide robust isolation against a malicious shared-key holder. Keys do not thereby grant access to our Vercel, GitHub or Supabase accounts. Report interference; do not claim tenant metadata is a security boundary or promise real funds/payout isolation.
